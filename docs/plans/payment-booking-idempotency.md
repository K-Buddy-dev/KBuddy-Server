# 결제 및 예약 멱등성 보장 계획

## 1. 문서 목적

결제 생성, 결제 승인, 채팅방 생성, 알림 처리에서 같은 요청이 반복되더라도 결과가 한 번만 생성되도록 개선한다.

이 단계는 [1단계 동시성 제어](./payment-booking-concurrency-control.md)가 완료된 후 진행한다.

## 2. 현재 문제

### 2.1 결제 생성의 조회 후 삽입 경쟁

현재 결제 생성은 다음 순서로 처리된다.

```text
bookingId로 결제 조회
→ 결제가 없으면 새 Payment 저장
```

같은 예약에 두 요청이 동시에 들어오면 두 요청 모두 결제가 없다고 판단할 수 있다. `payment.booking_id` 유니크 제약조건이 중복 저장은 막지만, 한 요청은 DB 예외와 함께 500 응답을 받을 수 있다.

### 2.2 결제 승인 재요청

다음 상황에서는 같은 승인 요청이 반복될 수 있다.

- 관리자가 승인 버튼을 여러 번 누름
- 네트워크 응답이 유실되어 클라이언트가 재시도함
- 향후 PG가 같은 웹훅을 여러 번 보냄

현재는 이미 승인된 결제에 다시 승인 요청이 들어오면 기존 성공 결과를 반환하지 않는다. 동시에 실행되면 채팅방과 알림 중복 생성도 시도할 수 있다.

### 2.3 입금 신고 재요청

`DEPOSIT_REPORTED` 상태에서 입금 신고를 다시 수행하면 다음 값이 덮어써진다.

- 입금자명
- 고객 메모
- 입금 신고 시각

단순 재시도와 의도적인 정보 수정을 구분하기 어렵다.

## 3. 목표 동작

| 요청 | 첫 번째 요청 | 같은 요청 재시도 | 같은 키의 다른 요청 |
|---|---|---|---|
| 결제 생성 | 결제 생성 | 기존 결제 반환 | 충돌 응답 |
| 결제 승인 | 승인 처리 | 기존 성공 결과 반환 | 충돌 응답 |
| 입금 신고 | 신고 처리 | 기존 결과 반환 | 수정 정책에 따라 거부 또는 별도 처리 |
| 채팅방 생성 | 채팅방 생성 | 기존 채팅방 반환 | 생성하지 않음 |
| 알림 이벤트 | 이벤트 생성 | 기존 이벤트 사용 | 생성하지 않음 |

## 4. 구현 계획

### 4.1 결제 생성의 유니크 충돌 처리

`payment.booking_id` 유니크 제약조건은 유지한다.

결제 저장 시 유니크 충돌이 발생하면 같은 `bookingId`의 결제를 다시 조회해 반환한다.

```text
Payment 저장 시도
├── 성공 → 생성된 결제 반환
└── booking_id 유니크 충돌
    → 기존 결제 재조회
    → 기존 결제 반환
```

모든 `DataIntegrityViolationException`을 같은 방식으로 처리하면 안 된다. 실제 제약조건이 `payment.booking_id` 중복인지 확인해야 한다.

### 4.2 멱등키 수신

결제 승인 요청은 `Idempotency-Key` 헤더를 받는다.

```http
Idempotency-Key: 5e30aee5-59f4-41da-852b-4b269387a46c
```

권장 규칙:

- UUID 형식 사용
- 최대 길이 제한
- 승인과 취소 등 작업별로 다른 키 사용
- 요청 본문을 정규화한 뒤 해시 저장

### 4.3 멱등성 테이블 추가

예시 구조:

```text
payment_idempotency
- id
- idempotency_key       UNIQUE
- operation
- payment_id
- request_hash
- processing_status
- response_status
- response_body
- created_at
- completed_at
```

처리 상태 예시:

```text
PROCESSING
COMPLETED
FAILED
```

### 4.4 멱등 요청 처리 흐름

```text
1. 멱등키와 작업 종류 조회
2. 기록이 없으면 PROCESSING으로 저장
3. 같은 키가 있으면 요청 해시 비교
4. 같은 요청이며 COMPLETED이면 기존 응답 반환
5. 같은 요청이며 PROCESSING이면 409 또는 202 반환
6. 다른 요청 내용이면 409 Conflict
7. 업무 처리 성공 후 응답 저장 및 COMPLETED 변경
```

멱등키 저장과 업무 상태 변경 사이의 원자성을 보장해야 한다.

### 4.5 이미 승인된 결제 처리

`Payment.status == PAID`이고 기존 승인 금액과 새 요청 금액이 같다면 기존 성공 결과를 반환한다.

요청 금액이 다르면 기존 성공으로 취급하지 않고 충돌 응답을 반환한다.

```text
PAID + 동일 금액
→ 기존 성공 결과

PAID + 다른 금액
→ 409 Conflict
```

### 4.6 채팅방 생성 멱등화

`chat_room.booking_id` 유니크 제약조건을 유지한다.

채팅방 생성은 `find-or-create` 방식으로 변경한다.

```text
bookingId로 채팅방 조회
├── 존재 → 기존 채팅방 반환
└── 없음 → 생성 시도
    ├── 성공 → 새 채팅방 반환
    └── 유니크 충돌 → 기존 채팅방 재조회 후 반환
```

### 4.7 알림 생성 멱등화

알림 또는 Outbox 이벤트에 업무 이벤트 키를 저장한다.

```text
PAYMENT_CONFIRMED:{paymentId}:CUSTOMER
PAYMENT_CONFIRMED:{paymentId}:COUNSELOR
```

이벤트 키에 유니크 제약조건을 적용해 같은 결제의 같은 수신자에게 알림 이벤트가 두 번 생성되지 않도록 한다.

## 5. 구현 대상 파일

| 대상 | 변경 내용 |
|---|---|
| `PaymentController` | 승인 요청의 멱등키 수신 |
| `PaymentService` | 기존 성공 결과 반환 및 결제 생성 충돌 처리 |
| `PaymentRepository` | 기존 결제 재조회 기능 사용 |
| 신규 멱등성 엔티티·저장소 | 키, 요청 해시, 처리 결과 저장 |
| `ChatRoomService` | `find-or-create` 방식 적용 |
| 알림 또는 Outbox 엔티티 | 이벤트 고유 키 추가 |
| DB 마이그레이션 | 멱등성 테이블과 유니크 인덱스 추가 |

## 6. 테스트 계획

### 6.1 결제 생성

- 같은 예약의 결제 생성 요청을 동시에 여러 번 호출
- 결제 행이 한 건만 생성되는지 확인
- 모든 요청이 같은 결제 ID를 받는지 확인
- 다른 DB 제약조건 오류는 기존 결제 반환으로 잘못 처리하지 않는지 확인

### 6.2 결제 승인

- 같은 멱등키와 같은 요청을 반복하면 기존 응답을 반환하는지 확인
- 같은 멱등키에 다른 금액을 보내면 `409 Conflict`인지 확인
- 이미 `PAID`인 결제에 같은 승인 요청을 보내도 상태 변경이 한 번인지 확인
- 처리 중인 멱등키가 다시 들어올 때 정의된 응답을 반환하는지 확인

### 6.3 후속 작업

- 승인 요청을 반복해도 채팅방이 한 개만 생성되는지 확인
- 고객과 상담사 알림이 각각 한 번만 생성되는지 확인
- 채팅방 저장 유니크 충돌 후 기존 채팅방을 반환하는지 확인

### 6.4 장애 상황

- 멱등성 기록 저장 후 업무 처리 실패
- 업무 처리 성공 후 응답 저장 실패
- 성공 응답 유실 후 같은 요청 재시도
- 프로세스 재시작 후 같은 키 재시도

## 7. 구현 순서

1. 결제 생성의 유니크 충돌을 기존 결제 반환으로 처리
2. 승인 요청 멱등키 저장
3. 이미 승인된 결제는 기존 성공 결과 반환
4. 채팅방 및 알림 생성 멱등화
5. 통합 테스트와 장애 테스트 추가

## 8. 완료 조건

- 같은 예약의 결제 생성 요청을 반복해도 결제가 한 건만 존재한다.
- 같은 승인 요청을 반복하면 같은 성공 결과를 반환한다.
- 같은 멱등키에 다른 요청을 보내면 거부된다.
- 채팅방과 알림 이벤트가 중복 생성되지 않는다.
- 서버 응답 유실 후 재시도해도 결제가 중복 처리되지 않는다.
- 멱등성 관련 통합 테스트가 PostgreSQL 환경에서 통과한다.
